# ADR-0008：測試用自寫的 Chrome DevTools protocol harness

- 狀態：已接受（2026-11-20 追認現況）
- 日期：2026-11-20（實作於 `ac28caa`）
- 決策者：開發者
- 對應需求：QS-005、CON-002、CON-006

## 背景
遊戲是畫布遊戲、狀態都在全域變數裡；要能自動驗證單人、多人與後台，又不想引入 npm 測試框架。

## 考慮過的選項
1. **npm 測試框架**（業界主流，例如 Playwright、Puppeteer）。
   - 切換代價：要 `npm install`（含下載瀏覽器）；20 個測試檔改寫成框架 API，大約一兩天；換來跨瀏覽器、截圖比對、追蹤等現成功能。
2. **自寫 harness**：用 Node 內建的 WebSocket 連到 headless Chrome／Edge 的 DevTools protocol；在測試副本注入 `__dbg(code)` 直接讀寫遊戲變數；多人測試自己起 server。
3. **只寫純邏輯的單元測試**（例如 `node:test`）。
   - 切換代價：遊戲邏輯跟畫布、DOM、全域狀態綁在一起，要先大量重構才能單獨測；也測不到多人與後台的整合。

## 決策
選項 2。

## 理由
- 開發環境盡量零依賴（CON-002）。
- 直接讀寫全域變數，比模擬滑鼠點畫布可靠。

## 後果
- 好處：`node tests/run.mjs` 就能跑；不用安裝套件。
- 代價：harness 要自己維護；本機要有 Chrome 或 Edge（CON-006）；沒有截圖比對等進階功能。
- 之後要注意：每個功能一個 `NN-name.mjs`；效能量測（R3）可以加在這個 harness。

## 重新檢視的條件
- 需要跨瀏覽器測試（CON-005 擴大時）。
- harness 本身的維護（新版 Chrome 的協定改變、不穩定的測試）在一個月內不只一次佔掉開發時間。
